# YUTU OS Design System

版本：1.0  
日期：2026-07-15  
適用專案：YUTU POS v2 / YUTU Operating System  
文件目的：建立 YUTU OS 的產品定位、資訊架構、導覽、命名、視覺層級與互動規範，作為後續 UI 調整及 Codex 開發的共同依據。

---

## 1. 核心定位

YUTU OS 是一套以咖啡店現場工作流程為前台、以營運紀錄為共同資料層的營運系統。

它不是把所有功能都壓縮成 POS，也不是把 POS 降格成單純的銷售事件輸入器，而是採用雙核心：

1. **現場工作核心（Operational Workflow Core）**  
   處理接客、開單、點餐、出品、換桌、結帳與日結等需要即時狀態與操作順序的工作。

2. **營運紀錄核心（Operational Record Core）**  
   處理銷售、製作、報廢、採購、自用、測試、招待、烘豆、盤點、維修等已發生且值得留存的營運事實。

簡化理解：

- POS 是駕駛艙。
- 營運事件是營運紀錄器。
- 庫存是由事件與盤點形成的現況。
- 經營分析是對營運資料的解讀。
- AI Agent 是依據紀錄提供提醒、預測與建議的助手。

## 2. 設計原則

### 2.1 Workflow First

首頁優先服務「現在正在做什麼」，而不是展示所有功能。

首頁主要任務：

- 接客
- 開單
- 點餐
- 出品
- 結帳
- 處理進行中的訂單

商品設定、歷史查詢、報廢、採購、分析、備份等功能不得與現場主流程爭奪主要視覺空間。

### 2.2 POS Remains Primary

主畫面仍是 POS Workspace。其他功能是由主畫面進入的工作區，而不是與 POS 並列、同等強調的七個大型按鈕。

### 2.3 Task Language, Not Database Language

導覽與頁面命名必須使用老闆知道「進去要做什麼」的語言，避免抽象或工程語言。

不佳：

- 資源管理
- 營運紀錄
- 備份與日結

較佳：

- 商品與原料
- 營運事件
- 訂單歷史
- 今日結帳／日結
- 資料備份

### 2.4 One Function, One Responsibility

每個頁面只回答一個主要問題：

- Workspace：現在要處理哪一組客人？
- 訂單歷史：過去完成了哪些訂單？
- 營運事件：今天還發生了哪些非訂單事件？
- 庫存現況：現在剩多少？
- 商品與資源：店裡有哪些可管理的主資料？
- 經營分析：最近營運表現如何？
- 系統：如何備份、同步與設定？

### 2.5 Frequency Determines Position

功能位置依實際使用頻率排序：

1. 每位客人都會使用：POS Workspace
2. 每日使用：訂單歷史、日結、營運事件
3. 每週使用：庫存、採購、烘豆、經營分析
4. 偶爾使用：商品設定、備份、系統設定
5. 例外／危險操作：不得放在全域第一層

### 2.6 Destructive Actions Are Contextual

「撤銷最後結帳」不得作為首頁永久導覽按鈕。

它應放在：

- 最近一筆已結帳訂單的詳細畫面；或
- 訂單歷史中的該筆訂單操作選單；或
- 結帳成功後的短時間 Undo 提示。

使用者必須看得見被撤銷的是哪一張訂單、時間、金額與桌位。

## 3. 使用者的五種工作模式

YUTU OS 的導覽以工作模式分類，而不是以資料表分類。

### 3.1 營業

目的：服務眼前的客人。

包含：

- POS 工作台
- 訂單佇列
- 目前訂單
- 座位狀態
- 外帶開單
- 出品狀態
- 結帳
- 訂單歷史
- 今日結帳／日結

### 3.2 紀錄

目的：補登或查看今天發生的營運事件。

包含：

- 製作
- 報廢
- 採購
- 自用
- 測試
- 招待
- 烘豆
- 盤點調整
- 維修／其他必要事件

第一版可沿用目前已實作的 purchase、waste、personal、test、complimentary，未實作類型以「規劃中」或不顯示處理，不建立空殼功能。

### 3.3 庫存

目的：查看現在剩多少，並追查數量變動來源。

包含：

- 庫存現況
- 甜點批次
- 熟豆批次
- 即將到期
- 低庫存提醒
- 盤點差異

庫存頁是「現況與追蹤」，不是另一套營運事件輸入系統。採購、製作、報廢等異動仍由營運事件建立。

### 3.4 管理

目的：維護不會隨每筆交易頻繁變動的主資料。

包含：

- 商品
- 原料／材料
- 設備
- 供應商
- 配方（未來）
- 成本設定（未來）

目前若只有商品與 inventoryLots，可先保留「商品」與「庫存」兩個明確入口，不要用模糊的「資源管理」包裝尚未完整的功能。

### 3.5 分析與系統

分析目的：了解店經營得怎麼樣。

- 經營分析
- 每日摘要
- 週期比較
- 商品排行
- 客源分析
- AI 建議（未來）

系統目的：維護資料與應用程式。

- 資料備份
- 資料匯入
- 同步狀態
- 系統設定
- 操作紀錄（未來）

## 4. 建議資訊架構

```text
YUTU OS
│
├── 營業
│   ├── POS 工作台（首頁）
│   ├── 訂單歷史
│   └── 今日結帳／日結
│
├── 紀錄
│   └── 營運事件
│       ├── 製作
│       ├── 報廢
│       ├── 採購
│       ├── 自用
│       ├── 測試
│       ├── 招待
│       ├── 烘豆（未來）
│       └── 盤點調整（未來）
│
├── 庫存
│   ├── 庫存現況
│   ├── 甜點批次
│   └── 熟豆批次
│
├── 管理
│   ├── 商品
│   ├── 原料（未來）
│   ├── 設備（未來）
│   └── 供應商（未來）
│
├── 分析
│   └── 經營分析

```

此架構不代表首頁顯示全部項目。第一層導覽應保持精簡，二級功能由抽屜、側欄或功能面板展開。

## 5. 主畫面導覽方案

### 5.1 不建議保留的現況

目前首頁將下列功能以相近尺寸、相同顏色並排：

- 商品管理
- 營運紀錄
- 資源管理
- 銷售紀錄
- 經營分析
- 備份與日結
- 撤銷最後結帳

問題：

- 「營運紀錄」與「銷售紀錄」語意接近。
- 「資源管理」無法預測內容。
- 「備份」與「日結」屬於不同使用情境。
- 危險操作與一般導覽同層。
- 使用頻率完全不同，卻具有相同視覺權重。
- 按鈕佔用 POS 工作台上方的大量空間。

### 5.2 建議桌面／平板版

使用固定但可收合的左側導覽，或頂部「功能選單」抽屜。

第一層順序：

1. **POS 工作台**
2. **訂單歷史**
3. **今日結帳**
4. 分隔線
5. **營運事件**
6. **庫存現況**
7. 分隔線
8. **商品**
9. **經營分析**
10. 分隔線
11. **資料與設定**

理由：

- 前三項都是營業流程。
- 中間兩項是每日營運紀錄與現況。
- 商品與分析屬管理／檢視。
- 系統功能最低頻，放最後。

### 5.3 首頁上方快捷區

若不立即導入側欄，可先將七顆按鈕縮減成四個清楚的入口：

1. **訂單歷史**
2. **營運事件**
3. **庫存現況**
4. **更多功能**

「更多功能」展開：

- 商品
- 經營分析
- 今日結帳
- 資料備份

但長期仍建議側欄／抽屜，因為功能數量會持續增加。

### 5.4 行動版／窄螢幕

底部導覽最多四項：

- 工作台
- 訂單
- 紀錄
- 更多

「更多」內再放庫存、商品、分析、資料與設定。

不建議在手機底部放六至七個入口。

## 6. 命名規範與現有功能改名

| 現有名稱 | 建議名稱 | 原因 |
|---|---|---|
| Cafe Workspace | POS 工作台 | 中文操作語意更直接；頁首可保留 YUTU POS 品牌名 |
| 商品管理 | 商品 | 頁面本身已代表可管理，不必重複「管理」 |
| 營運紀錄 | 營運事件 | 與銷售紀錄區隔，明確對應 BusinessEvent |
| 資源管理 | 庫存現況 | 現階段實際內容主要是甜點與熟豆批次，「資源」過度抽象 |
| 銷售紀錄 | 訂單歷史 | 資料來源是 paid orders；比「銷售」更貼近 POS 流程 |
| 銷售紀錄／日報 | 訂單歷史 | 日報摘要可作為頁面中的日期摘要，不需要放進標題 |
| 經營分析 | 經營分析 | 可保留 |
| 備份與日結 | 資料與日結（過渡） | 短期若尚未拆頁，可先明確分成兩區 |
| 備份與日結 | 今日結帳 + 資料備份（目標） | 長期拆成營業流程與系統功能 |
| 撤銷最後結帳 | 撤銷此筆結帳 | 必須在明確訂單脈絡下使用 |

### 6.1 頁面標題與說明文字

每個二級頁面應有一句簡短說明，降低名稱相近造成的混淆。

- **訂單歷史**：查看已完成訂單、日營收與訂單明細。
- **營運事件**：記錄採購、報廢、自用、測試與招待等非銷售事件。
- **庫存現況**：查看甜點與熟豆批次、剩餘數量與到期狀態。
- **商品**：設定 POS 可販售品項、售價、成本與販售狀態。
- **經營分析**：比較營收、商品、時段、座位與客源表現。
- **今日結帳**：確認今日未結訂單並產生當日結帳資料。
- **資料備份**：匯出或還原完整營運資料。

## 7. 顏色與視覺層級

### 7.1 顏色不是用來替每個按鈕染色

主畫面應維持 YUTU 的暖白、木質、咖啡色系。功能分組色只作為小面積識別，例如圖示、左側指示線、標籤或選取狀態，不應讓畫面變成多色管理後台。

### 7.2 建議語意色

- **營業／主要操作**：深咖啡或深綠  
  用於主要按鈕、營業狀態、結帳等正向操作。

- **紀錄／提醒**：暖橘或琥珀  
  用於營運事件、待補登提醒、即將到期。

- **庫存／管理**：灰藍或柔和棕灰  
  用於庫存、商品、原料等中性管理功能。

- **分析**：低飽和紫灰或藍灰  
  只作識別，不與主要操作競爭。

- **系統**：中性灰  
  用於備份、匯入、設定。

- **危險**：紅色  
  只用於刪除、清空、撤銷結帳、覆蓋資料等高風險操作。不得用紅色作一般導航裝飾。

### 7.3 按鈕層級

1. Primary：當前工作流程的下一步，例如開始、儲存、結帳。
2. Secondary：同頁替代操作，例如編輯、切換模式。
3. Tertiary／Ghost：導覽、查看明細、取消。
4. Danger：刪除、清空、撤銷、覆蓋。

同一區塊最多一個 Primary Action。

### 7.4 圖示

圖示必須搭配文字，不以圖示單獨傳達重要功能。

建議：

- 工作台：杯子／收銀
- 訂單歷史：收據／時鐘
- 今日結帳：日曆勾選
- 營運事件：筆記／加號
- 庫存：箱子／層架
- 商品：標籤／菜單
- 經營分析：趨勢圖
- 資料與設定：齒輪／資料庫

避免目前座位使用不同風格 Emoji 所造成的視覺不一致；未來可統一使用同一套 SVG icon。

## 8. 主畫面版面建議

### 8.1 頁首

保留：

- YUTU POS／POS 工作台
- 日期
- 營業狀態
- 開店／關店主要動作
- 導覽選單按鈕

開發版本提示應保留但降低高度與視覺權重，不應比工作台標題更突出。

### 8.2 工作區主體

建議順序：

1. 營業摘要：空位、進行中、待出品、可結帳
2. 座位／開單區
3. Order Queue
4. Current Order

「Current Store State / Cafe Workspace」重複顯示，應精簡為單一區塊名稱，例如「今日狀態」。

### 8.3 導覽不占用主工作寬度

首頁七顆跳轉按鈕應移出工作內容主列。可採：

- 左側收合式導覽；或
- 頁首右側「功能」按鈕打開抽屜；或
- 桌面側欄＋平板抽屜的響應式方案。

### 8.4 空白狀態

右側 Current Order 空白狀態目前資訊重複：「選擇桌位或工作／從 Workspace 開始處理下一步」。

建議改成：

**尚未選擇訂單**  
點選左側座位、外帶訂單或 Order Queue 開始處理。

若無任何訂單，可顯示主動作「新增外帶」；不要同時出現多個不明確提示。

## 9. 重複功能與職責整理

### 9.1 訂單歷史 vs 營運事件

不得合併。

- 訂單歷史：POS 完成訂單的查詢與修正入口。
- 營運事件：非訂單的營運紀錄入口。

二者可在分析層共同被讀取，但操作流程不同。

### 9.2 營運事件 vs 庫存

不得重複建立同一筆異動。

- 採購、製作、報廢、盤點調整：建立事件。
- 庫存現況：讀取事件／批次並呈現剩餘狀態。

若目前 inventoryLots 仍獨立保存批次資料，需在文件中定義其與 BusinessEvent 的責任邊界，避免同一件採購或報廢被輸入兩次。

### 9.3 商品 vs 庫存資源

- 商品：可販售的 POS 品項與售價設定。
- 庫存品／原料：被採購、使用、製作或盤點的實體資源。

同一名稱可能同時存在商品與原料，但必須由 ID／來源欄位連結，不可只靠文字名稱推測。

### 9.4 日結 vs 備份

必須拆開職責：

- 日結：營業流程，確認今日訂單、產生每日摘要與關店結果。
- 備份：系統維護，匯出完整資料以供還原。

即使短期同頁實作，也必須分成兩個清楚的區塊，不能只用同一個標題混合。

### 9.5 撤銷結帳 vs 編輯已結帳訂單

目前兩者都能使已結帳資料回到可變動狀態，風險與用途重疊。

建議定義：

- 撤銷結帳：結帳後短時間內，針對明確指定訂單，快速回復 open。
- 修正已結帳訂單：由訂單歷史進入，要求填寫修正原因，保留活動紀錄；不應只靠把 paid 改回 open 而失去稽核語意。

短期至少要把兩個入口放在訂單詳細脈絡中，不放首頁。

## 10. 互動規範

### 10.1 頁面切換

- 切換管理／分析頁後，必須有明確「返回 POS 工作台」。
- 有未保存表單時，離頁前提醒。
- 返回工作台時保留目前 open order 與選取狀態，除非資料已失效。

### 10.2 建立營運事件

流程：

1. 選擇事件類型
2. 選擇品項來源／輸入名稱
3. 輸入數量、單位、金額或成本
4. 選填原因、供應商、備註
5. 確認摘要
6. 儲存

常用類型可做快速卡片，但事件紀錄列表與新增表單應在同一工作區，不需要每一類型都另做一個頂層頁面。

### 10.3 高風險操作

匯入備份、刪除歷史訂單、撤銷結帳、清空資料需顯示：

- 影響對象
- 影響時間／日期
- 不可逆性
- 主要識別資訊

禁止只顯示泛用 confirm：「確定嗎？」

### 10.4 成功提示

成功提示應說明結果，例如：

- 已記錄報廢：巴斯克 1 份。
- 已完成 7 月 15 日日結，共 8 張訂單、營收 2,340 元。
- 已撤銷 18:42 吧台前訂單結帳，訂單已回到進行中。

## 11. 第一階段實作範圍

第一階段只調整 IA、命名、導覽與風險入口，不重構資料模型，不新增尚未確認的大型功能。

### 必做

1. 將首頁七顆等權重按鈕移出主內容或縮減為分組導覽。

- 不大幅改動目前結帳、同步與資料 schema。
- 不重做整套視覺品牌。

## 12. 驗收標準

### 資訊架構

- 第一次看到畫面的人能區分「訂單歷史」與「營運事件」。
- 「庫存現況」名稱能合理預測頁面內容。
- 日結與備份在視覺與操作上有清楚區隔。
- 危險操作不出現在首頁一般導覽中。

### 現場流程

- POS 工作台仍是預設首頁。
- 開單、點餐、出品、結帳所需步驟不得增加。
- 切換至其他頁面再返回時，不遺失目前訂單狀態。
- 平板上主要工作區保持足夠寬度。

### 視覺

- 一般導覽不再全部使用相同大小與相同權重。
- 每個畫面只有一個明確的主要操作。
- 紅色只用於風險／錯誤，不用於一般分類。
- 功能分組可辨識，但不使用高飽和多色拼貼。

### 程式品質

- `npm.cmd run build` 成功。
- 不破壞現有訂單、商品、營運事件、inventoryLots 與分析資料。
- 不變更既有 backup schema，除非另有 migration 與文件更新。
- 更新相關文件：CURRENT_STATUS、BUSINESS_RULES、ARCHITECTURE、UX_REVIEW。

## 13. 後續發展原則

新增任何功能前，先回答：

1. 它屬於現場工作、營運紀錄、庫存現況、主資料、分析，還是系統？
2. 使用者是要「做事」、「補紀錄」、「看現況」還是「理解趨勢」？
3. 是否已經有另一頁在記錄同一件事？
4. 它需要出現在第一層導覽嗎？使用頻率是否足夠？
5. 它是否會打斷 POS 主流程？
6. 它會建立新資料，還是只讀取現有資料？
7. 若是危險操作，是否在明確對象脈絡中執行？

不符合上述原則的功能，不應直接新增首頁按鈕。

## 14. 最終設計結論

YUTU OS 的主畫面仍是 POS 工作台，因為 POS 承載即時且連續的現場工作流程。其他功能依「營業、紀錄、庫存、管理、分析、系統」分組，並透過清楚命名與視覺層級降低混淆。

此次調整的重點不是增加功能，而是：

- 讓每個入口的用途一眼可理解。
- 將相近但不同的功能清楚分開。
- 把危險操作移回正確脈絡。
- 保留 POS 作為產品主角。
- 為未來製作、報廢、庫存、烘豆、AI Agent 等功能建立可持續擴充的導航規則。
